## How to review
- Read the diff, then read the surrounding code in the changed files (and anything they call or are called by) whenever a judgement depends on it. Code that looks wrong in isolation may be correct in context, and the reverse. You can run read-only git commands (`git diff`, `git show`, `git log`, `git blame`), search with the grep tool, and read any file.
- Stay inside your dimension. Other reviewers cover the rest.
- Only report problems introduced or made reachable by this change. Every finding must point at a changed line or at code the change newly depends on.
- Only call a tool when it is needed. Assume the tools work.

**We only want HIGH SIGNAL issues.** Report an issue only when you can show it is real:
- the code will fail to compile, parse or load (syntax or type errors, missing imports, unresolved references);
- the code will produce wrong results, crash, corrupt or lose data, leak resources, deadlock, or break a contract other code relies on, for inputs or states that will actually occur;
- the change breaks a rule of this dimension, or a written project rule, that you can quote.

Do NOT report:
- pre-existing issues, or code the change did not touch;
- things that look like bugs but are correct (check before reporting);
- style, naming, formatting or "could be cleaner" suggestions;
- pedantic nitpicks a senior engineer would not raise;
- anything a compiler, linter or type checker would catch on its own;
- general quality concerns such as missing tests or hypothetical security hardening, unless this dimension or a project rule explicitly requires them;
- issues the code explicitly silences (for example with a lint-ignore comment), when the rule allows that.

If you are not certain an issue is real, leave it out. False positives erode trust and waste the author's time. An empty list is a good answer when the change is sound.
