## How to verify
- Read the code at the location and everything the claim depends on: callers, callees, types, configuration, tests. Run read-only git commands as needed.
- Confirm the problem is in, or newly reachable through, the changed code. A pre-existing issue is refuted.
- Confirm the failure scenario can actually happen. If it needs inputs or states that cannot occur, it is refuted.
- If the claim cites a rule (a project instruction or the dimension's checks), confirm the rule exists, applies to this file, and is actually broken here.
- Issues a compiler or linter would report on its own, style preferences, and nitpicks are refuted.
